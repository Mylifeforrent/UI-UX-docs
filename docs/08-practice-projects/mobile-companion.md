# 练习项目：移动端配套应用

这是 Web 工作台之后的适配练习。不要把桌面表格缩小，而是从同一业务模型中提取一个高频、低时长任务：主管在移动端查看待审批订单并完成审批。

## 任务范围

```text
通知入口 → 待审批列表 → 订单摘要 → 查看关键风险 → 批准/驳回 → 结果确认
```

共享 [Web 工作台](web-workbench.md) 的订单状态和权限，但重新设计导航、内容优先级和中断恢复。

## 必须做出的平台决策

| 议题 | iOS | Android | 共同要求 |
| --- | --- | --- | --- |
| 顶层导航 | Tab Bar | Bottom Navigation | 不超过 4--5 个高频入口 |
| 返回 | 导航栏返回/边缘返回 | 系统返回键/手势 | 返回栈可预测，不丢未提交内容 |
| 确认 | Action Sheet 或 Alert | Dialog 或 Bottom Sheet | 危险动作说明对象和影响 |
| 权限 | 系统权限说明后请求 | 系统权限说明后请求 | 只在需要时请求，拒绝后可恢复 |
| 安全区 | 刘海、Home Indicator | 状态栏、导航栏 | 内容不被系统区域遮挡 |

## 状态与中断

- 网络断开时保留已加载的订单摘要，标注离线并禁用需要服务端确认的审批动作。
- 审批请求进行中锁定按钮，返回时提示任务仍在处理，避免重复提交。
- 被系统挂起后恢复，重新校验订单版本；若已被他人处理，显示冲突而不是覆盖。
- 推送通知只作为入口，进入页面后仍需重新拉取权限和最新状态。
- 表单或驳回意见未完成时，返回或手势退出要有保存草稿/放弃选择。

## 触控与可访问性

主要操作区域至少保持可触控尺寸，文字、状态和图标同时表达信息。不要把滑动删除作为唯一删除方式；为键盘、辅助技术和误触提供明确替代路径。滚动列表需要保留加载、空态、错误和重试位置。

## 交付步骤

1. 从 [App 信息架构](../03-app-design/information-architecture.md) 提取移动任务和导航。
2. 用 [导航与手势](../03-app-design/navigation-gestures.md) 画返回栈和中断流程。
3. 用 [平台适配](../03-app-design/platform-adaptation.md) 记录 iOS/Android 差异。
4. 复用 Web 的业务 [Design Token](../04-design-system/tokens.md)，但按平台替换交互组件。
5. 对正常、离线、权限不足、冲突和部分加载状态做原型和验收。

## 通过标准

- 主管可在 60 秒内从通知进入并完成一次审批。
- 审批失败、网络中断、订单被他人更新时，用户知道发生了什么并能恢复。
- iOS 和 Android 都遵循各自返回、系统区域和权限习惯。
- 关键任务不依赖单一手势，且不会因键盘或长文本遮挡主按钮。
