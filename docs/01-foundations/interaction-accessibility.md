# 交互与无障碍

企业界面不是把控件摆上去就完成。每个动作都要定义默认、悬停/聚焦、进行中、成功、失败和禁用状态，并让用户知道下一步怎么做。状态、文案和反馈规则应进入 [验收清单](../06-engineering-workflow/acceptance-checklist.md)。

## 可测量最低线

- 主流程可以只用键盘完成；Tab 顺序与任务顺序一致，不把焦点送进不可见区域。
- 聚焦状态始终可见；对话框打开后焦点进入，关闭后回到触发控件；Esc 和取消行为明确。
- 文本与背景达到 WCAG 2.2 AA 的对比度目标：普通文本至少 4.5:1，大字号文本至少 3:1；非文本控件边界和焦点也要可辨识。
- Web 交互目标建议至少 24×24 CSS px，移动端主要触控目标按平台规范留出更大点击区域；不要用视觉尺寸掩盖实际可点击区域。
- 图片、图标按钮、表单控件都有可理解的名称；装饰图标使用空替代文本或从辅助技术树隐藏。
- 状态不只靠颜色表达：用文字、图标、位置或 aria 属性补充“待审批/已驳回”等含义。

## 语义实现

优先使用原生 HTML：`button` 执行动作，`a` 负责导航，`label` 关联表单，`table` 表达真正的二维数据。只有原生元素无法满足时才添加 ARIA；ARIA 不能修复错误的键盘行为。

```html
<label for="order-query">搜索订单</label>
<input id="order-query" name="query" aria-describedby="query-help query-error">
<p id="query-help">支持订单号或客户名称</p>
<p id="query-error" role="alert">请输入至少 2 个字符</p>
```

## 表单错误

错误靠近字段，指出原因和修复方式；提交后把焦点移到第一个错误字段，并保留用户已经填写的内容。服务端校验错误要能映射到字段或表单级摘要，不能只显示通用 Toast。

## 对话框与抽屉

打开时保存触发控件，设置可访问名称，把焦点移入；关闭时恢复焦点。背景内容不可操作但不能从辅助技术中制造无法退出的焦点陷阱。危险操作的确认文案写清对象、影响和后果，例如“批准 3 个订单”比“确定吗？”更可判断。

## 人工与自动检查

自动化可以检查颜色对比、缺少 label、重复 ID 和部分键盘规则；人工仍需完成一次完整键盘路径、放大文字后的布局检查、屏幕阅读器朗读顺序和错误恢复。记录浏览器、视口、步骤和证据，写入 [视觉验收记录](../templates/visual-acceptance.md)。
