# Prompt 与上下文

AI 结果的稳定性主要取决于上下文是否完整。每轮 Prompt 都写清目标、约束、输出格式、验收条件和不能改变的部分。

## 基础结构

```text
角色：企业内部运营人员
任务：筛选并批量处理订单
页面：订单列表、详情抽屉、批量审批
上下文：UI Brief、页面清单、Token、组件清单、API 契约
约束：桌面优先；支持空态、错误、权限不足；危险操作可恢复
输出：先给状态矩阵，再给组件和页面方案，最后列出待确认问题
禁止修改：业务权限、API 字段名、既有 Token 名称
验收：首屏主任务清晰；状态完整；长内容不溢出
```

## 可复制任务模板

### 产品分析

```text
请从这份 PRD 提取角色、对象、任务、权限、风险、成功条件和失败恢复。不要设计视觉。输出 7 列 Markdown 表格，并列出缺失信息。
```

### 状态矩阵

```text
请针对页面清单中的每个页面输出默认、加载、空数据、无结果、错误、无权限、部分数据和成功状态。每行写“用户看到什么/能做什么/不能做什么”。不要新增业务状态。
```

### Coding Agent

```text
根据 UI Brief、组件清单、Token 和 API 契约实现页面。先列出路由、组件、数据状态和测试计划，等确认后再写代码。禁止新增颜色、间距、权限和 API 字段。
```

### 截图修正

```text
根据截图和视觉验收记录，只修复 P1 的容器对齐问题。保持路由、文案、Token、数据和交互不变。先说明根因和将修改的文件，再提交最小改动，并按同一视口截图回归。
```

## 上下文分层

稳定规则放在仓库文档或 Agent 指令；项目范围放在 [UI Brief](../templates/ui-brief.md)；页面和组件状态放在清单；一次性问题放在 [视觉验收记录](../templates/visual-acceptance.md)。不要每轮重复粘贴生产数据，使用脱敏 fixture 和最小必要上下文。
