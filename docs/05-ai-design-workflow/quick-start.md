# AI 设计工作流快速入门指南

本文档是 [AI 设计工作流](README.md) 的快速入门版，帮助你在 30 分钟内理解核心概念，1 天内跑通第一个项目。

## 5 分钟：核心理念

### 一句话总结

**企业级 AI 工作流 = 结构化输入 + 自动化门禁 + 可审计输出**

### 三个关键转变

| 从 | 到 | 价值 |
| --- | --- | --- |
| 聊天式对话 | 文档驱动 | 可复现、可复用 |
| 人工检查 | 自动化门禁 | 快速反馈、降低遗漏 |
| "大概对" | 度量驱动 | 持续改进、可量化 |

### 你会得到什么

- ⏱️ **提速 40-60%**：原型 3 天 → 1.2 天，开发 10 天 → 6 天
- 📉 **返工率降低 50%**：平均返工 2 次 → 1 次
- 📊 **质量可度量**：视觉一致性 96%+，测试覆盖率 80%+
- 🔄 **流程可复制**：新人上手时间从 2 周 → 3 天

## 10 分钟：理解框架

### 六个阶段（G0-G6）

```text
G0 立项 → G1 上下文 → G2 原型 → G3 设计基线 → G4 契约 → G5 实现 → G6 验收
   ↓         ↓          ↓           ↓             ↓          ↓          ↓
 治理     建模       快速生成    规范化       对齐      AI辅助     自动化
        UI Brief   Figma Make   Token      PRD    代码生成    门禁
```

**每个阶段都有**：
- 明确的入口条件（前置依赖）
- 标准的产出物（可版本化）
- 硬性的门禁检查（通过才能继续）
- 清晰的责任人（RACI）

### 五个成熟度级别

```text
L0: 对话驱动 → 不可复现，靠运气
L1: 上下文完整 → 有 Brief/清单/状态矩阵
L2: 规则固化 → 有 Token/组件库/仓库规则
L3: 门禁自动 → CI 自动拦截质量问题
L4: 可审计度量 → 数据驱动流程改进
```

**建议**：从 L0 开始，每 2-4 周提升一级，不要跳级。

### 三个不变量

| 不变量 | 含义 | 违反后果 |
| --- | --- | --- |
| **上下文是资产** | 规则写进仓库，随代码版本化 | 换人/换模型结果就变 |
| **门禁是硬约束** | 未通过门禁不进下游 | 错误被复制到下游 |
| **证据是交付物** | 截图/记录与代码同版本 | 无法定位返工原因 |

### 最小工具集（L1 级别）

## 30 分钟：跑通第一个页面

### 场景：实现一个登录页

**时间分配**：
- 准备输入（10 分钟）
- AI 生成（5 分钟）
- 人工审查和调整（10 分钟）
- 对比总结（5 分钟）

### 步骤 1：准备输入（10 分钟）

**创建 `docs/login-brief.md`**：

```markdown
## 目标
企业员工通过邮箱和密码登录内部系统

## 角色与权限
- 已注册员工：可登录
- 未注册员工：显示"请联系 IT 部门"

## 页面状态矩阵

| 状态 | 用户看到什么 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 默认 | 邮箱、密码输入框，登录按钮，忘记密码链接 | 输入、提交 | - |
| 提交中 | 按钮文本"登录中..."，输入框禁用 | 等待 | 重复提交 |
| 成功 | "登录成功"提示 | 等待跳转 | - |
| 失败 | "邮箱或密码错误"，密码清空 | 重新输入 | - |
| 锁定 | "账号已锁定 30 分钟" | 查看说明 | 提交表单 |
| 无网络 | "网络连接失败"，重试按钮 | 点击重试 | - |

## 约束
- 桌面优先（1440px）
- 品牌色：蓝色 #0066FF
- 支持键盘 Tab 导航
```

### 步骤 2：AI 生成（5 分钟）

**Prompt**（复制到 Claude Code）：

```markdown
## Context
任务：实现登录页面（/login）
业务需求：@docs/login-brief.md
技术栈：React + TypeScript + Tailwind CSS

## Role
前端工程师，10 年经验

## Action
实现登录页面，包括：
1. 表单布局（居中，卡片样式）
2. 表单验证（邮箱格式、必填）
3. 状态矩阵中的 6 种状态
4. 键盘导航支持

先输出实现计划，等我确认后再写代码。

## Format
- 计划：Markdown 列表
- 代码：Markdown 代码块（标注文件路径）

## Test
- [ ] 所有状态都有对应 UI
- [ ] 邮箱格式校验实时反馈
- [ ] Tab 键可导航所有元素
- [ ] 连续 5 次失败显示锁定态

## Constraints
- 使用 Tailwind utility classes
- 颜色使用 blue-600（临时，后续改 Token）
- 数据先用 fixture，不连接真实 API
```

等待 AI 输出计划，确认后让它继续输出代码。

### 步骤 3：人工审查（10 分钟）

**检查清单**：

```markdown
视觉检查:
- [ ] 布局居中，卡片有阴影和圆角
- [ ] 输入框有边框和 focus 样式
- [ ] 按钮有 hover 和 disabled 状态

功能检查:
- [ ] 邮箱格式错误时显示提示
- [ ] 提交中按钮禁用
- [ ] 成功/失败状态文案正确

无障碍检查:
- [ ] Tab 键顺序：邮箱 → 密码 → 按钮 → 链接
- [ ] 输入框有 label
- [ ] 错误提示有 aria-describedby

状态覆盖:
- [ ] 6 种状态都能复现（用 fixture 模拟）
```

### 步骤 4：对比总结（5 分钟）

**记录发现**：

```markdown
## 对比：临时 Prompt vs 结构化 Brief

| 维度 | 临时方式 | Brief 方式 | 差异 |
| --- | --- | --- | --- |
| 输入时间 | 2 分钟 | 10 分钟 | +8 分钟 |
| 生成质量 | 遗漏 2 个状态 | 覆盖完整 | - |
| 返工次数 | 3 次 | 1 次 | -2 次 |
| 总耗时 | 45 分钟 | 30 分钟 | -15 分钟 |

## 关键收获
- Brief 的 10 分钟投入，节省了 15 分钟返工
- 状态矩阵强制覆盖边界情况
- 下次做注册页，复用 Brief 结构只需 5 分钟
```

**恭喜！** 你已经完成了从 L0 到 L1 的第一步。

## 1 天：完整项目实操

选择一个真实的小项目（如内部工具的一个页面），按照以下流程完整走一遍：

### 上午：准备阶段（3-4 小时）

**G0 立项**（30 分钟）：
- 明确业务目标和用户
- 确认数据分级（是否涉及敏感信息）
- 评估 AI 工具准入（见 [治理与风险](governance-and-risk.md)）

**G1 上下文建立**（2-3 小时）：
- 竞品分析（如有）：截图 + 拆解
- 填写 UI Brief（目标、角色、任务、风险）
- 创建页面清单（路由、功能、优先级）
- 创建组件清单（复用 vs 新建）
- 生成状态矩阵（8 种标准状态）

**产出物检查**：
- [ ] UI Brief 必填字段完整
- [ ] 状态矩阵包含 8 种状态
- [ ] 风险任务有失败恢复机制

### 下午：生成与验证（3-4 小时）

**G2 原型**（1-2 小时）：
- 使用 Figma Make 或 AI 生成原型（可选）
- 或直接用文本描述交互（无 Figma 时）
- 人工评审：主流程可走通，状态完整

**G5 实现**（2 小时）：
- 按 [Prompt 模板](prompting-and-context.md#可复制任务模板库) 编写 Prompt
- AI 生成代码（分步：计划 → 代码 → 测试）
- 本地运行和手工测试

**G6 验收**（30 分钟）：
- 固定视口截图（1440 / 768 / 390）
- 对照 Brief 验收标准逐条检查
- 记录问题和改进点

**产出物检查**：
- [ ] 代码通过 ESLint
- [ ] 8 种状态都能复现
- [ ] 键盘可完成主流程
- [ ] 有基础测试用例

### 晚上：复盘与沉淀（30 分钟）

**回顾会议**（记录到 `docs/retrospectives/YYYY-MM-DD.md`）：

```markdown
## 项目回顾

**项目**: [页面名称]
**日期**: 2026-08-24
**参与人**: [名字]

### 度量数据
- 输入准备: 3.5 小时
- AI 生成: 0.5 小时
- 人工调整: 1.5 小时
- 验收: 0.5 小时
- 总计: 6 小时（传统方式预计 10 小时）

### 做得好的
1. Brief 结构化输入让 AI 一次生成了 80% 可用代码
2. 状态矩阵避免了遗漏边界情况
3. 分步生成（计划→代码）降低了返工

### 需要改进的
1. Brief 中遗漏了"忘记密码"流程，后续补充
2. 没有提前定义 Design Token，颜色硬编码了
3. 测试用例覆盖不完整

### 下次行动
- [ ] 建立 Token 文件（下周）
- [ ] 补充测试模板到 Prompt 库
- [ ] Brief 增加"明确不做"章节
```

## 常见问题速查

### Q: 我是个人开发者，需要这么复杂的流程吗？

**A**: 不需要完整流程，但建议：
- 最小采用：Brief + 状态矩阵（L1）
- 收益：避免遗漏状态，减少返工
- 成本：每个页面多 10 分钟准备

### Q: 团队抵制变化怎么办？

**A**: 渐进式推进：
1. 选一个非关键项目试点
2. 用数据对比（时长、返工次数）
3. 第一个成功案例后，自然会有人跟进
4. 不要强制全员切换，允许并行存在

### Q: AI 工具经常出错怎么办？

**A**: 检查三个方面：
1. **上下文完整性**：Brief、Token、组件清单是否齐全？
2. **Prompt 明确性**：约束和验收标准是否清晰？
3. **门禁覆盖**：是否有自动化检查拦截错误？

大部分"AI 错误"实际是输入不完整。

### Q: 如何说服老板投入？

**A**: 准备三个数据：
1. **ROI 计算**：工具成本 vs 节省工时（见 [README](README.md#常见问题)）
2. **试点数据**：小项目的时长对比
3. **风险对比**：治理框架 vs 无管控的风险

强调"不是增加成本，而是降低隐性成本"。
