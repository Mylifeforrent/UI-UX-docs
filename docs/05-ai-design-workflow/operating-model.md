# 运作模型

企业级 AI 设计工作流的核心是**可预测、可审计、可度量**。本文定义阶段划分、角色职责、交付物标准和质量度量指标。

## 阶段与门禁

每个阶段有明确的**入口条件**、**产出物**、**门禁检查**和**责任人**。未通过门禁的产物不得进入下游。

| 阶段 | 入口条件 | 核心产出 | 门禁检查 | 责任人 | 典型时长 |
| --- | --- | --- | --- | --- | --- |
| G0 立项 | 业务需求、目标用户、优先级 | 项目章程、数据分级、风险评估 | 安全与合规审批 | 产品负责人 | 2-5 天 |
| G1 上下文建立 | G0 通过、竞品分析完成 | UI Brief、页面清单、组件清单、状态矩阵 | 业务模型完整性检查 | 产品设计师 + BA | 3-5 天 |
| G2 原型设计 | G1 产出齐全 | Figma 可交互原型（全状态） | 用户流程可走通、状态覆盖完整 | UI/UX 设计师 | 3-7 天 |
| G3 设计基线 | G2 评审通过 | Design Token、组件库、设计规范 | Token 命名规范、组件可复用性 | 设计系统负责人 | 2-3 天 |
| G4 契约定义 | G3 完成、技术评审通过 | PRD、API 契约、Code Connect 映射 | 接口完整性、前后端对齐 | 产品经理 + 架构师 | 2-4 天 |
| G5 开发实现 | G4 契约签署 | 生产代码、单元测试、集成测试 | 代码规范、测试覆盖率、安全扫描 | 前端工程师 | 5-10 天 |
| G6 验收交付 | G5 自测通过 | 视觉回归报告、验收清单、部署文档 | UAT 通过、性能达标、无障碍合规 | QA + 产品 | 2-3 天 |

### 门禁细则

每道门禁由**自动检查**和**人工审查**组成：

#### G1 门禁：上下文完整性

**自动检查**：
- UI Brief 包含所有必填章节（目标、角色、权限、风险任务）
- 页面清单至少覆盖主流程的 3 个核心页面
- 状态矩阵包含 8 种标准状态（默认/加载/空/无结果/错误/无权限/成功/失败）

**人工审查**：
- 业务分析师确认角色与权限模型准确
- 产品负责人确认风险任务的恢复机制合理

#### G2 门禁：原型可用性

**自动检查**：
- 所有 Frame 已命名（格式：`/{route}/{state}`）
- 布局使用 Auto Layout（绝对定位比例 < 5%）
- 无未解决的设计评审问题（P0/P1）

**人工审查**：
- 用户研究员验证主任务流程可在 3 次点击内完成
- 无障碍专员检查焦点顺序和屏幕阅读器标注

#### G3 门禁：设计系统一致性

**自动检查**：
- 所有颜色值来自 Design Token（硬编码颜色 = 0）
- 组件命名符合规范（PascalCase，无重复）
- Token 变量已导出为 CSS Variables 或 JSON

**人工审查**：
- 设计系统负责人确认新组件不与现有组件冲突
- 前端架构师确认 Token 结构可映射到代码

#### G5 门禁：代码质量

**自动检查**（CI 流水线）：
```yaml
质量门禁:
  - ESLint/Prettier 通过（0 error）
  - 单元测试覆盖率 ≥ 80%
  - 无高危安全漏洞（npm audit/Snyk）
  - Bundle size 增量 < 50KB（gzip）
  - Lighthouse Accessibility ≥ 90
```

**人工审查**：
- 代码审查（至少 1 位 Senior 批准）
- 危险操作二次确认机制验证
- API 错误处理覆盖率检查

#### G6 门禁：交付标准

**自动检查**：
- 视觉回归测试通过（像素差异 < 0.1%）
- 4 个标准视口截图已归档（390/768/1024/1440）
- 性能指标达标（LCP < 2.5s, FID < 100ms, CLS < 0.1）

**人工审查**：
- UAT 场景 100% 通过
- 产品验收清单签字
- 部署 Runbook 可执行

## RACI 矩阵

明确每个阶段的角色职责，避免"都负责 = 都不负责"。

| 阶段 | 产品负责人 | BA | UI/UX 设计师 | 前端工程师 | QA | 安全/合规 |
| --- | --- | --- | --- | --- | --- | --- |
| G0 立项 | **A** | C | I | I | I | **R** |
| G1 上下文 | **A** | **R** | **R** | C | I | I |
| G2 原型 | **A** | C | **R** | C | I | I |
| G3 设计基线 | C | I | **A/R** | C | I | I |
| G4 契约 | **A** | C | C | **R** | C | I |
| G5 开发 | C | I | C | **A/R** | C | I |
| G6 验收 | **A** | I | C | C | **R** | C |

**图例**：
- **R** (Responsible): 执行者，完成工作
- **A** (Accountable): 负责人，最终决策和签字
- **C** (Consulted): 顾问，提供输入
- **I** (Informed): 知情人，接收通知

## 产出物登记

每个阶段的产出物必须**版本化**、**可追溯**、**有责任人签字**。

### 产出物清单模板

```markdown
## 阶段产出物登记表

| 产出物 | 版本 | 创建日期 | 责任人 | 存储位置 | 状态 | 签字 |
| --- | --- | --- | --- | --- | --- | --- |
| UI Brief | v1.2 | 2026-08-20 | Alice | docs/ui-brief.md | 已批准 | ✅ Bob |
| 原型文件 | v2.0 | 2026-08-22 | Carol | figma.com/file/xxx | 已冻结 | ✅ Dave |
| PRD | v1.0 | 2026-08-23 | Bob | docs/prd.md | 草稿 | ⏳ |
```

### 版本化规则

- **主版本号**：通过门禁后递增（如 v1.0 → v2.0）
- **次版本号**：门禁前的迭代（如 v1.1 → v1.2）
- **冻结标记**：通过 G2 门禁的原型必须标记"已冻结"，后续修改需走变更流程

### 变更控制

门禁通过后的产出物修改需要**变更请求**（Change Request, CR）：

```markdown
## 变更请求模板

**CR 编号**: CR-2026-08-24-001
**请求人**: Alice
**影响阶段**: G2 原型
**变更原因**: 用户反馈批量操作入口不够明显
**影响范围**: /approvals 页面顶部操作栏
**风险评估**: 低风险，不影响 API 契约
**批准人**: Bob (产品负责人)
**状态**: 待批准
```

## 度量指标

用数据驱动改进，而不是靠感觉。每个迭代结束后收集以下指标。

### 过程指标

| 指标 | 定义 | 目标值 | 采集方式 |
| --- | --- | --- | --- |
| 门禁通过率 | 首次提交通过门禁的比例 | ≥ 80% | CI/CD 日志 |
| 返工次数 | 通过门禁后因质量问题退回的次数 | ≤ 1 次/阶段 | Git commit history + CR 记录 |
| 平均阶段时长 | 从阶段开始到通过门禁的天数 | 见上表"典型时长" | 项目管理工具 |
| 上下文完整性 | UI Brief/清单/状态矩阵的必填字段填充率 | 100% | 自动化脚本检查 |

### 质量指标

| 指标 | 定义 | 目标值 | 采集方式 |
| --- | --- | --- | --- |
| 设计一致性得分 | 使用既有 Token 和组件的比例 | ≥ 95% | Figma 插件扫描 |
| 测试覆盖率 | 单元测试覆盖的代码行百分比 | ≥ 80% | Jest/Vitest 报告 |
| 可访问性得分 | Lighthouse Accessibility 分数 | ≥ 90 | CI 中的 Lighthouse |
| 视觉还原度 | 实现与设计稿的像素匹配度 | ≥ 98% | Percy/Chromatic |

### 效能指标

| 指标 | 定义 | 目标值 | 采集方式 |
| --- | --- | --- | --- |
| AI 生成代码采纳率 | AI 生成的代码直接合并的比例 | ≥ 60% | Git diff + PR 标签 |
| 人工修正成本 | 修复 AI 输出所需的平均时间 | ≤ 20% 总开发时间 | 工时统计 |
| 端到端交付周期 | 从 G0 到 G6 的总天数 | ≤ 30 天（单页） | 项目计划 vs 实际 |
| 缺陷密度 | UAT 阶段发现的缺陷数/功能点 | ≤ 2 个/页面 | 缺陷跟踪系统 |

### 度量仪表板示例

```markdown
## 本迭代度量报告（2026-08-01 ~ 2026-08-24）

### 过程健康度
- ✅ 门禁通过率: 85% (目标 80%)
- ⚠️ 返工次数: 平均 1.5 次/阶段 (目标 ≤1)
- ✅ 平均阶段时长: 在目标范围内

### 质量健康度
- ✅ 设计一致性: 97%
- ✅ 测试覆盖率: 82%
- ⚠️ 可访问性: 平均 88 分 (目标 90)
- ✅ 视觉还原度: 99.2%

### 效能健康度
- ✅ AI 代码采纳率: 68%
- ✅ 人工修正成本: 15%
- ✅ 端到端周期: 27 天
- ✅ 缺陷密度: 1.2 个/页面

### 改进行动
1. **返工次数偏高**: 加强 G1 阶段的业务建模评审
2. **可访问性未达标**: 在 G2 门禁增加键盘导航检查
```

## 工具链集成

将门禁检查嵌入工具链，减少人工负担。

### 推荐工具栈

| 阶段 | 自动化工具 | 用途 |
| --- | --- | --- |
| G1 | 自定义脚本 | 检查 UI Brief/清单的必填字段 |
| G2 | Figma 插件 (Design Lint) | 检查命名规范、布局方式 |
| G3 | Figma Variables Exporter | 自动导出 Token 为 CSS/JSON |
| G5 | ESLint + Stylelint | 代码规范检查 |
| G5 | Axe DevTools | 无障碍自动检查 |
| G6 | Percy/Chromatic | 视觉回归测试 |
| 全流程 | Linear/Jira | 产出物登记和工作流状态跟踪 |

### CI/CD 流水线示例

```yaml
name: Quality Gate G5

on:
  pull_request:
    branches: [main]

jobs:
  quality-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Install dependencies
        run: npm ci
      
      - name: Lint
        run: npm run lint
      
      - name: Type check
        run: npm run type-check
      
      - name: Unit tests
        run: npm run test:coverage
      
      - name: Coverage check
        run: |
          COVERAGE=$(jq '.total.lines.pct' coverage/coverage-summary.json)
          if (( $(echo "$COVERAGE < 80" | bc -l) )); then
            echo "Coverage $COVERAGE% is below 80%"
            exit 1
          fi
      
      - name: Security audit
        run: npm audit --audit-level=high
      
      - name: Bundle size check
        uses: andresz1/size-limit-action@v1
      
      - name: Accessibility check
        run: npm run test:a11y
      
      - name: Visual regression
        uses: chromaui/action@v1
        with:
          projectToken: ${{ secrets.CHROMATIC_TOKEN }}
```

## 审计与复盘

每个项目完成后进行**回顾会议**，记录：

1. **什么做得好**：哪些实践提高了质量或效率
2. **什么需要改进**：哪些门禁失效、哪些返工可避免
3. **行动计划**：下个项目优先改进的 3 件事

将回顾结果写入 `docs/retrospectives/YYYY-MM-DD.md`，作为流程改进的输入。

## 企业级扩展

### 多团队协作

当多个团队并行开发时：

- **统一设计系统**：所有团队共享同一套 Token 和组件库
- **API 契约优先**：G4 阶段由架构师统一评审，避免接口冲突
- **视觉回归共享**：使用 Chromatic 等工具的团队工作区

### 合规与审计

对于受监管行业（金融、医疗）：

- G0 增加**数据保护影响评估** (DPIA)
- G4 增加**安全架构评审** (SAR)
- G6 增加**合规证据包**（截图、测试报告、签字表）

### 知识沉淀

建立**案例库**：

```text
docs/case-studies/
  approval-workflow/        # 审批工作流案例
    ui-brief.md             # 输入
    design-review.md        # 评审记录
    prd.md                  # PRD
    visual-acceptance.md    # 验收记录
    retrospective.md        # 复盘
```

新项目启动时，从案例库中选择最相似的作为模板。

## 下一步

- 如果你的团队刚开始，先跑通一个页面的完整流程，建立信心
- 如果你已经有部分流程，对照 RACI 矩阵找到职责空白
- 如果你要推广，先定义 3 个关键度量指标，用数据说话
