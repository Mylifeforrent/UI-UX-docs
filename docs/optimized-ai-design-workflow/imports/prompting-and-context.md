# Prompt 与上下文

← 返回 [原型先行全流程主文档](prototype-first-workflow.md)

这是整套流程里复用率最高的一份文档。全流程每一步的 Prompt 都遵循这里的写法。核心一句话：**给 AI 写 Prompt，等于给下游写接口契约——约束就是校验规则，输出格式就是返回类型，验收标准就是单元测试断言。** 后端开发者天然擅长这件事，只是换了个对象。

## 为什么后端程序员反而有优势

你每天写接口时都在做同样的事：定义入参、出参、校验规则、错误码、幂等约束。写 Prompt 就是把这套思维迁移到"设计"这个不确定的黑盒上。UI 设计师凭直觉补全的空白，你用**显式约束**补全，效果往往更稳定、更可回归。

不熟悉 UI 的人最容易犯的错，是把 Prompt 写成一句"帮我做个好看的审批页面"——这等于写一个 `doSomething()` 接口，没有入参、没有契约。结果不可控、不可复现、无法验收。

## 六要素模板（每个 Prompt 都应包含）

| 要素 | 作用 | 后端类比 |
| --- | --- | --- |
| **角色** | 锚定 AI 的专业视角和输出风格 | 选择实现类 / 依赖注入 |
| **任务** | 一句话说清这一轮要产出什么 | 方法名 + 目的 |
| **上下文** | 喂入已确定的事实（Brief、状态矩阵、令牌…） | 入参 / 依赖数据 |
| **约束** | 划定不可逾越的边界 | 参数校验 + 业务规则 |
| **输出格式** | 规定产物形态，便于下一步消费 | 返回类型 / DTO |
| **验收与禁改项** | 可判定的完成标准 + 明确不许动什么 | 单测断言 + 幂等/副作用约束 |

一个合格 Prompt 的骨架：

```text
你是[角色]。                          ← 角色
本轮任务：[一句话产出目标]。            ← 任务
已知上下文：[粘贴 Brief / 状态矩阵 / 令牌 / 组件清单，或给文件路径]。  ← 上下文
约束：
- [边界1]；[边界2]；[边界3]。          ← 约束
输出：[Markdown 表格 / 页面清单 / 代码 …，规定结构]。  ← 输出格式
验收：[可逐条判定的标准]；
禁止：[不要新增未提及的能力 / 不要改动其他页面 / 不造新数据]。  ← 验收与禁改项
```

## 逐要素：好 / 坏对比

### 角色

- ❌ 坏：`帮我设计一下`（无角色，AI 用通用泛泛视角）
- ✅ 好：`你是企业 SaaS 产品设计师，服务对象是每天处理上百条审批的运营主管`
- 要点：角色越具体，AI 越会带出行业默认（如企业软件重密度、重键盘操作、轻装饰）。

### 任务

- ❌ 坏：`把这个页面做好`（"好"不可判定）
- ✅ 好：`本轮只产出 /approvals 页面的状态矩阵，不生成界面`
- 要点：一轮一个明确产物。想要多个产物，拆成多轮。

### 上下文

- ❌ 坏：`按我们的规范来`（AI 不知道你的规范）
- ✅ 好：`已知：颜色间距令牌见 tokens.css（附内容）；组件用 component-inventory.md 里已定义的 OrderTable / StatusBadge，不要新建同义组件`
- 要点：AI 没有记忆，也读不到你脑子里的事实。把已确定的东西**显式贴进去或给出文件路径**。上下文缺失是原型跑偏的头号原因。

### 约束

- ❌ 坏：`不要太复杂`（模糊）
- ✅ 好：`危险操作（驳回）必须弹二次确认并强制填写理由；桌面 1440 宽优先，附 375 宽手机版；只使用给定文案，不造新数据`
- 要点：约束要能被"违反"才有意义。写成可检查的具体条款。

### 输出格式

- ❌ 坏：`告诉我你的想法`（自由文本，下一步没法消费）
- ✅ 好：`输出 Markdown 五列表：角色 | 对象 | 高频任务 | 风险任务 | 完成条件`
- 要点：规定结构，让产物能直接粘进模板或喂给下一轮。

### 验收与禁改项

- ❌ 坏：（省略——最常见的错误）
- ✅ 好：`验收：每个高频任务都有入口和完成条件，每个风险任务都有失败恢复路径。禁止：新增输入里没有的业务能力；改动其他页面布局。`
- 要点：**禁改项**在迭代阶段尤其关键，否则 AI 会顺手"优化"你已经定稿的部分，造成回归。

## 上下文管理：喂什么、怎么喂

1. **分层喂入**：先喂事实（Brief、状态矩阵、令牌、组件清单），再下指令。不要把事实和指令混在一段话里。
2. **一次一任务**：不要一个 Prompt 让 AI"生成全部页面全部状态"。单轮任务越聚焦，质量越高、越好回滚。
3. **迭代用"锁定 + 增量"句式**：

   ```text
   保持其他页面和布局完全不变。本轮只修改空数据状态：
   标题改为"暂无待审批订单"，副文案"新任务会出现在这里"，
   提供"查看已审批"次级链接，主按钮在此状态下禁用。
   ```

4. **给路径优于贴长文**：当 AI 能读取文件时（如本地 Coding Agent），给 `docs/prd-approvals.md` 这样的路径比粘贴几千字更可靠、更省 token。
5. **让 AI 先复述计划**：关键步骤（生成页面、写代码）先要求"先输出实现计划/页面清单，等我确认再动手"。这是最便宜的纠偏点。

## 可复用片段库

把这些片段拼进任意 Prompt，减少重复劳动。

**角色前缀**

```text
你是企业 SaaS 产品设计师，熟悉高信息密度后台、键盘优先操作和无障碍规范。
```

**通用约束清单**

```text
约束：
- 只使用给定的文案、数据和令牌，不臆造新内容；
- 只使用已定义的组件，不新建同义组件；
- 危险/不可逆操作必须二次确认；
- 桌面 1440 优先，附 375 手机版；
- 覆盖状态矩阵里的每一个状态。
```

**禁改项清单（迭代时必带）**

```text
禁止：改动本轮任务之外的任何页面、布局、组件和文案；禁止新增未在上下文中出现的业务能力。
```

**验收前缀**

```text
验收（逐条可判定）：
```

## 常见误区

| 误区 | 后果 | 纠正 |
| --- | --- | --- |
| 一句话 Prompt | 产物不可控、不可复现 | 补齐六要素 |
| 事实和指令混写 | AI 抓不住重点 | 分层：先事实后指令 |
| 不写验收标准 | 无法判断"做完了没" | 每轮都写可判定验收 |
| 迭代时不写禁改项 | AI 顺手改坏已定稿部分 | 每次迭代锁定其余内容 |
| 一轮塞多个任务 | 质量下降、难回滚 | 一次一任务 |
| 假设 AI 记得上文 | 上下文丢失、跑偏 | 每轮显式重述关键事实或给路径 |
