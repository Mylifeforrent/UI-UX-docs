# 视觉评审闭环

← 返回 [原型先行全流程主文档](prototype-first-workflow.md)

第 8 步的验收方法。目标：用可复现的截图，逐条对照 PRD 验收标准，把"感觉不对"变成"第 3 条不达标"。

## 为什么要固定视口截图

后端开发者习惯"跑一遍看日志"。视觉验收的等价物是：**在固定视口、用固定 fixture 渲染每个状态，截图归档**。视口和数据一固定，截图就可复现、可对比、可回归——和快照测试是一回事。

## 步骤

1. **准备 fixture**：为每个状态准备一份固定假数据（默认/加载/空/无结果/错误/无权限/成功/部分失败）。不要用随机数据，否则截图不可比。
2. **固定视口**：桌面 1440 宽、手机 375 宽两档。每个状态两档各截一张。
3. **渲染并截图**：逐状态切换、逐档截图，命名 = 路由 + 状态 + 视口，如 `approvals-empty-1440.png`。
4. **逐条对照**：打开 PRD 的验收标准，一条一条勾。问题记入 [视觉验收记录](../templates/visual-acceptance.md)。
5. **问题分类回流**：
   - **代码问题**（数据绑定、状态切换、样式实现）→ 回第 7 步改代码。
   - **设计问题**（信息层级、文案、缺状态）→ 回第 4 步迭代原型，再重走。
   - **切忌**：发现不一致就整页重新生成——那会丢掉已验证的部分。

## 检查要点（逐状态过）

- 长文案不溢出（客户名 20 字、金额千分位、超长错误信息）
- 空态和错误态有具体文案与可行动作，不是"这里显示错误"
- 危险操作流程能走完并正确回到列表
- 键盘可达：Tab 顺序合理、焦点可见
- 桌面/手机关键差异符合设计（如表格→摘要卡片）

## 与验收清单的关系

本闭环只管"看得见的"部分。功能、权限、性能等完整交付项，见 [交付验收清单](../06-engineering-workflow/acceptance-checklist.md)。
